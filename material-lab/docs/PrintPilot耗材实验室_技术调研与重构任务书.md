## 2. 产品目标

这个系统首先要帮助用户回答：

1. 我有哪些耗材、分别还有多少？
2. 某个品牌和产品系列有哪些颜色，我买了哪些颜色？
3. 商家、厂家和 Bambu Studio 分别给了什么参数或预设？
4. 同一个产品的资料是否冲突？冲突来自哪里？
5. 某个颜色或批次经过我实测后，什么参数更可靠？
6. 当我下次打印时，怎样快速找到这款耗材的可靠资料，而不用重新翻聊天记录、商品页和本地文件？

核心体验应该是：

```text
建立产品系列
 → 维护系列颜色
 → 录入当前库存
 → 上传商家截图、PDF、客服原话和预设
 → 系统整理出可追溯的产品资料
 → 显示厂家参数、Bambu 预设、个人实测及冲突
 → 后续可以继续补资料、盘点和校准
```

## 3. 不能理解错的业务规则

技术实现可以推翻，下面这些业务语义不能随意改变。

### 3.1 产品与颜色

- 商家提供的打印参数、物理性能和机械性能通常属于**产品系列**。
- 商家颜色名属于该产品系列下的**颜色规格**。
- 商家颜色名必须原样保留，例如“土壤棕”“电光蓝”“棉花白”，不能只保存成“棕色”“蓝色”“白色”。
- 系统还需要给颜色映射一个标准色系，便于跨品牌查找和统计；标准色系可以人工修正。
- 厂家提供整个系列的颜色表时，需要维护完整系列颜色目录，即使某些颜色当前没有库存。
- 某种颜色的温度塔、流量、K/PA、异常和批次反馈属于颜色或批次层，不能错误覆盖整个产品系列。

推荐的领域关系是：

```text
产品系列
├── 产品级厂家/商家资料
├── 厂家预设与 Bambu Studio 预设
└── 颜色规格
    ├── 库存
    ├── 颜色级资料
    └── 颜色/批次/机器/喷嘴实测
```

### 3.2 库存

- 这是人工盘点库存，不按每次打印任务自动扣料。
- 用户自己或让 AI 执行新增、减少和修正。
- `1.5 卷`表示“1 卷未开封 + 当前开封卷剩余约 50%”。
- 最直观的保存方式可以继续拆成：未开封整卷数 + 当前开封卷余量百分比。
- 需要快捷盘点、调整、撤销、目标库存和补货清单。
- 不需要为每卷耗材建立复杂的唯一资产档案。

### 3.3 资料、事实与冲突

- 原始截图、图片、PDF、网页资料、客服原话、JSON/BBSFLMT 预设都要保留。
- 结构化参数必须能够追溯到原始资料。
- 厂家事实、商家描述、Bambu Studio 系统预设、厂家预设、用户预设和个人实测要区分来源身份。
- 两个来源给出不同数值时，应同时保留并提示冲突，不能静默覆盖。
- 资料中暂时没有进入固定字段体系的内容也要留存，不能因为数据库没有对应列就丢弃。
- 图片识别或 AI 提取只生成草稿，确认后再进入正式资料。
- 同一个原始文件应按 SHA-256 去重。

### 3.4 预设与校准

- 如果 Bambu Studio 已有品牌和型号完全匹配的预设，应同步并用于比较。
- 相似材料只能标记为参考基线，不能冒充完全匹配。
- 厂家提供的预设属于厂家参数；个人流量比例、K/PA、最大体积流量和温度塔属于个人实测。
- 厂家事实不能被个人校准覆盖，个人校准也不能被后续资料上传抹掉。
- 最大体积流量不能从“最高打印速度”直接推导，只能来自明确预设或实测。
- 低温增稳板使用 BIQU Glacier（必趣冰川）基准：PLA 50 ℃、PETG 65 ℃。

## 14. Codex 当前意见（供参考，不约束 Grok）

当前架构中，SQLite、本地文件、Caddy 和 React 本身并没有明显选错。主要维护成本来自自写 HTTP 层、手工前后端契约、巨型文件和逐步堆叠的页面流程。

Codex 倾向于保留 SQLite、本地文件和 Caddy，考虑用 FastAPI/Pydantic/OpenAPI 现代化后端，并重构 React 的页面和数据请求边界。但这只是一个参考假设。Grok 可以用一个结构更整洁、实际更好用的完整版本推翻它。

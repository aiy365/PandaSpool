## 一、整体健康度评价

| 维度 | 评分 | 说明 |
|---|---|---|
| 功能正确性 | ⭐⭐ (2/5) | 产品模块因列/参数错位**处于不可用状态**，且是静默失败 |
| 安全性 | ⭐ (1/5) | 鉴权中间件是空壳、SQL 注入实测可 `DROP TABLE`、前端 4 处 XSS |

**综合：4.2 / 10 — 「骨架健康，内脏出血」**

架构分层是对的：原生 `net/http` + `database/sql` + `go:embed` 的组合非常克制，没有引入不必要的重型依赖，`internal/bambu/bambu.go` 里对拓竹 MQTT 状态机的处理（`PrintingFromState` / `stageName` / JWT 解析）看得出是踩过坑的人写的，质量不错。

但这个项目现在**带着三个会让数据静默损坏或直接丢库的缺陷在跑**，而且全部集中在最近加入的 `bambu_preset_id` 和 spools 短编号两个特性上。这两个补丁是「贴上去」的，没有同步更新配套的 SQL 语句。

**必须今晚修的三件事：**
1. `products` 表的 INSERT/UPDATE 参数错位 → 数据写错列、更新静默失效
2. `NextShortCode` 的 SQL 注入 → 实测可删表
3. `auth` 中间件是空实现 → 所有 API 裸奔

## 二、P0 高危漏洞

### P0-1 `products` 表 SELECT/INSERT/UPDATE 列与参数错位 —— 静默数据损坏 **[实测]**

`bambu_preset_id` 列加入后，`SELECT` 少一列、`INSERT`/`UPDATE` 少一个占位符，但 `Scan`/`Exec` 的参数却多了一个。

**致命的是 modernc.org/sqlite 不校验参数个数**，多余参数被静默丢弃 —— 于是错误不会抛出，数据会写进**错误的列**。

实测输出：

```
INSERT SaveProduct -> err=<nil>
ROW brand="B" material="PLA" notes="" created="" preset=""
UPDATE SaveProduct -> err=<nil>
after update brand="B" notes=""        ← 更新完全没有生效
ListProducts -> err=sql: expected 6 destination arguments in Scan, not 7
```

逐条拆解：

| 语句 | 占位符 | 实参 | 实际后果 |
|---|---|---|---|
| `INSERT INTO products(id,brand,product_line,material,notes,created_at)` | 6 | 7 | `notes` 列被写入 `BambuPresetID`，`created_at` 列被写入 `Notes`，真正的 `CreatedAt` 被丢弃 |
| `UPDATE products SET brand=?,product_line=?,material=?,notes=? WHERE id=?` | 5 | 6 | `WHERE id` 被绑定成 `p.Notes` → 匹配 0 行 → **任何产品编辑都是无效操作** |
| `SELECT id,brand,product_line,material,notes,created_at` | 6 列 | 7 个 Scan 目标 | 直接报错 → 产品列表 100% 白屏 |

`ListProducts` 报错还会在 `spoolIntake` 里级联触发 500 —— 也就是说**耗材入库功能现在是彻底坏的**。

### P0-2 `NextShortCode` 字符串拼接 SQL —— 实测可 `DROP TABLE` **[实测]**

```go
// internal/store/spool.go:94  当前代码
err := s.DB.QueryRow(fmt.Sprintf(
    `SELECT short_code FROM spools WHERE short_code LIKE '%s%%' ORDER BY CAST(SUBSTR(short_code, %d) AS INTEGER) DESC LIMIT 1`,
    prefix, len(prefix)+1)).Scan(&maxCode)
```

`prefix` 直接 `fmt.Sprintf` 进 SQL。实测注入：

```
NextShortCode("x'; DROP TABLE spools; --") -> "x'; DROP TABLE spools; --001"  err=<nil>
随后 SELECT COUNT(*) FROM spools  ->  SQL logic error: no such table: spools (1)
```

**`spools` 表被成功删除。**

调用链是可达的：`POST /api/spools` → `spoolIntake` → `prefix = getInitial(brand) + getInitial(colorName)` → `NextShortCode(prefix)`。目前 `getInitial` 只返回首字符，压缩了攻击面（单字符很难构造有效 payload），但这是**巧合而非防护** —— 只要有人给 `getInitial` 加个「返回前两个字母」的改动，或者新增一个直接传用户字符串调 `NextShortCode` 的接口，立刻变成任意 SQL 执行。

顺带一提，`fmt.Sscanf(maxCode.String, prefix+"%d", &seq)` 也坏：如果 `prefix` 里含 `%`，格式串直接被破坏。

```diff
+const maxShortCodeSeq = 9999

+var errShortCodeExhausted = errors.New("短编号序列已用尽")

 func (s *Store) NextShortCode(prefix string) (string, error) {
+	// prefix 参与 LIKE 匹配与 Sscanf 格式串，必须先约束再使用。
+	// 短编号只可能是 ASCII 字母数字与常见分隔符。
+	if prefix != "" && !isShortCodePrefix(prefix) {
+		return "", fmt.Errorf("非法的短编号前缀: %q", prefix)
+	}

-	err := s.DB.QueryRow(fmt.Sprintf(`SELECT short_code FROM spools WHERE short_code LIKE '%s%%' ORDER BY CAST(SUBSTR(short_code, %d) AS INTEGER) DESC LIMIT 1`, prefix, len(prefix)+1)).Scan(&maxCode)
+	// 参数化 LIKE；SUBSTR 起始位置也走参数，杜绝一切拼接。
+	err := s.DB.QueryRow(
+		`SELECT short_code FROM spools
+		  WHERE short_code LIKE ? ESCAPE '\'
+		  ORDER BY CAST(SUBSTR(short_code, ?) AS INTEGER) DESC
+		  LIMIT 1`,

+	).Scan(&maxCode)

 	}

-		_, _ = fmt.Sscanf(maxCode.String, prefix+"%d", &seq)
+		// 用 TrimPrefix + Atoi 代替 Sscanf，避免 prefix 中的 % 破坏格式串。
+		if n, convErr := strconv.Atoi(strings.TrimPrefix(maxCode.String, prefix)); convErr == nil {
+			seq = n
+		}
 	}
 	seq++
+	if seq > maxShortCodeSeq {
+		return "", errShortCodeExhausted
+	}
 	return fmt.Sprintf("%s%03d", prefix, seq), nil

+// isShortCodePrefix 只允许 [A-Za-z0-9] 与 - _ . 作为前缀，长度 1..8。
+func isShortCodePrefix(s string) bool {
+	if s == "" || len(s) > 8 {
+		return false
+	}
+	for i := 0; i < len(s); i++ {
+		c := s[i]
+		switch {
+		case c >= 'a' && c <= 'z', c >= 'A' && c <= 'Z', c >= '0' && c <= '9':
+		case c == '-' || c == '_' || c == '.':
+		default:
+			return false
+		}
+	}
+	return true
+}
+
+// likeEscape 转义 LIKE 通配符，防止前缀里的 % 和 _ 被当作通配符匹配到无关行。
+func likeEscape(s string) string {
+	return strings.NewReplacer(`\`, `\\`, `%`, `\%`, `_`, `\_`).Replace(s)
+}
```

### P0-3 鉴权中间件是空壳 —— 所有 API 未经授权可访问


被 `s.auth(...)` 包裹的 30+ 个路由全部形同虚设，包括：

- `POST /api/settings` —— 覆盖拓竹账号密码、eWeLink AppSecret、萤石 AppKey
- `DELETE /api/products/{id}` —— 删除产品及其全部颜色/claim

- `GET /api/settings` —— 虽然有 `Redact()`，但那只在有的路径上生效

即使监听在 `127.0.0.1:8088`，这依然是**可利用的 CSRF**：用户浏览器打开任意恶意页面，`fetch('http://127.0.0.1:8088/api/settings', {method:'POST', ...})` 就能改掉凭据（无 token、无 SameSite 校验、无 Origin 检查）。这个项目定位是「私有化中控枢纽」，一旦有人挂到局域网或反代后面，等于把家里打印机和摄像头的凭据公开。

### P1-3 SQLite 并发配置不够健壮

当前 DSN：

```go
dsn := filepath.Join(dataDir, "app.sqlite3") + "?_pragma=busy_timeout(5000)&_pragma=foreign_keys(ON)&_pragma=journal_mode(WAL)"
```

WAL 和 busy_timeout 都开了，方向对，但缺三样东西：

1. **没有 `SetMaxOpenConns`** —— 默认无上限。一个并发高峰会打开几十条连接，其中 N-1 条立刻撞 `SQLITE_BUSY`，然后在 busy handler 里空转烧 CPU。
2. **没有 `_txlock=immediate`** —— 默认是 deferred 事务：先拿读锁，写的时候再升级。两个连接同时「读→升级写」会形成**无法靠 busy_timeout 解除的死锁**，直接返回 `SQLITE_BUSY_DEADLOCK`。
3. **没有 `synchronous=NORMAL`** —— WAL 模式下 `FULL` 是没必要的 fsync 开销，性能差 2-3 倍，而 WAL 本身的持久性保证已经足够。

```diff
+	// 若将来出现读多写重的负载，再改成分离的读写双池（见下方说明）。
+	db.SetMaxOpenConns(1)
+	db.SetMaxIdleConns(1)
+	db.SetConnMaxLifetime(0)
+
+	// 立刻验证连得上，别等到第一次请求才炸。
+	if err := db.Ping(); err != nil {
+		db.Close()
+		return nil, fmt.Errorf("sqlite ping: %w", err)
+	}
```

> **什么时候不该用 `MaxOpenConns(1)`**：如果某个 handler 里有慢查询（比如 `/api/compare` 全表扫 claims 再 join），它会堵住整条连接，导致所有请求排队。如果确实遇到，改成分离读写双池：`writeDB`（`MaxOpenConns(1)`）+ `readDB`（`MaxOpenConns(N)`，走 WAL 快照读）。以本项目的数据量（几百个料盘、几千条 claim），单连接完全够用。

## 五、架构解耦：用 Interface 隔离第三方云

### 现状问题

`spool_api.go` 里到处是 `bambu.NewCloudAdapter(cfg.Bambu.Region, cfg.Bambu.AccessToken)` —— 4 个 handler 各 new 一次。这带来三个麻烦：

1. **无法单元测试** —— 测 `spoolIntake` 就必须真的调拓竹云
2. **无法替换** —— 想接自建 SpoolMan 或本地 MQTT AMS 桥接，得改遍所有 handler
3. **每次请求重建 adapter** —— 连带重建 `http.Client`，连接池和 TLS 会话完全没复用（这也是 P1-1 的性能问题之一）

### 方案：在使用方定义接口

Go 的惯例是「接口由使用方定义」，所以不需要新建 `internal/cloud` 包（那反而会引入 `bambu` 和 `server` 的循环依赖），直接在 `server` 包里声明它需要的能力：

```go
// internal/server/cloud.go
package server

import (
	"context"
	"pandaspool/internal/bambu"
)

// FilamentCloud 是 server 对"远端耗材账本"的全部需求。
// 拓竹云是当前唯一实现，但换成本地 SpoolMan 或测试桩都不需要改 handler。
type FilamentCloud interface {
	ListFilaments(ctx context.Context) ([]bambu.CloudFilament, error)
	CreateFilament(ctx context.Context, f bambu.CloudFilament) (int64, error)
	UpdateWeight(ctx context.Context, id int64, name string, netWeightG int) error
	DeleteFilaments(ctx context.Context, ids []int64) error
}

// 编译期断言：真实实现与测试桩都必须满足契约。
// 这一行的价值在于——改动 bambu.CloudAdapter 签名时会立刻编译失败，
// 而不是等到线上调用时 panic。
var _ FilamentCloud = (*bambu.CloudAdapter)(nil)
```

注入到 `Server`：


### 同样的模式可以用在 eWeLink / 萤石

`machine` / `actuator` / `camera` 三个 handler 同样直接依赖 `ewelink.Client` 和 `ezviz.Client`。抽出：

```go
// 环境中控：开关/插座类设备
type SwitchController interface {
	Devices(ctx context.Context) ([]Device, error)
	Switch(ctx context.Context, id string, on bool) error
}

// 摄像头
type CameraProvider interface {
	AccessToken(ctx context.Context) (string, error)
	Status(ctx context.Context) map[string]any
}
```

其中 `Device` 是 `server` 包自己的 DTO（不复用 `ewelink.Device`），这样 `ewelink.Device` 的字段变动不会波及 handler —— 这才是真正的解耦。
